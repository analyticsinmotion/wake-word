# Wake Word - VS Code Extension

## Commands

```bash
npm install                # Install dependencies
npm run compile            # Build TypeScript to dist/
npm run watch              # Build in watch mode
npm run lint               # Run ESLint (flat config, eslint.config.mjs) + SVG check on README.md. Do not use --fix.
npm test                   # Run the unit test suite once (vitest)
npm run test:watch         # Run the unit tests in watch mode
npm run package            # Build .vsix package
npm run benchmark          # Acoustic benchmark over tests/acoustic/fixtures (manual; needs `npm run compile` and sherpa-onnx installed with --no-save; reads the model in models/)

# Engine packaging (after `cargo build --release` in engine-rs/)
node engine-rs/scripts/stage.mjs --target win32-x64             # Engine, ONNX Runtime, Silero model into bin/
npx vsce package --target win32-x64 -o ww.vsix                  # Package with bin/ included
node scripts/verify-vsix.mjs --target win32-x64 --vsix ww.vsix --extract-to <dir>   # Check the package, run its self-test
bin/wake-word-engine --self-test                                # What the binary found, without opening a microphone
bin/wake-word-engine --list-devices                             # The input devices, as one DEVICES: line of JSON
```

`--self-test` opens no microphone and loads no keyword spotting model, so it is
safe to run anywhere; it does load the voice activity model, which is what makes
it report a missing inference runtime. CI runs it on all four platforms, from
the unpacked package. `--list-devices` opens no microphone and loads nothing:
see Input devices below.

Run `npm run lint`, `npm run compile`, and `npm test` before committing. All
three must pass cleanly. For a change under `engine-rs/`, also run
`cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, and
`cargo test` there; CI fails on any of them too.

Press F5 in VS Code to launch the Extension Development Host for manual testing.

`extension.ts` owns all VS Code API interactions. `sherpaEngine.ts` implements `ISpeechEngine` on every platform. The engine is a child process, the binary in `bin/`, never code in the extension host. Keep this separation clean.

`wakeWordCore.ts` holds the pure logic the extension host and the engine share: phrase normalisation, route validation, the stdout protocol parser, the debounce guard, the confirmation check, the threshold clamp, the handoff order (`releaseThenFire()`), which routes' commands are available and what to tell the user about the others, which routes are switched off and what the switch command writes, the status bar's states and which one the extension's facts lead to, the phrase quality and collision checks, and the diagnostics report. It imports nothing from `vscode`, so it is directly unit testable. Put shared pure logic there rather than inline in `extension.ts`.

## Architecture

The extension builds its speech engine with `createEngine()`, which returns a `SherpaEngine` on every platform, and wires it with `wireEngine()`. The engine's child communicates via stdout: `READY`, `DETECTED:<phrase>|<confidence>` (the confidence suffix is optional, and the child never sends it), `PAUSED`, `RELEASED`, `ERROR:<message>`, and `DEBUG:<info>`. After its config line the child also reads commands on stdin: `pause`, `resume`, `stop`, `debug on`, and `debug off`. The extension reads stdout, matches phrases, and fires VS Code commands. All events are logged to a dedicated "Wake Word" output channel, a log channel whose level the user sets (see The verbose log). Besides `started`, `paused`, `stopped`, `detected`, and `error`, `SherpaEngine` emits `restarting` (see Fatal errors and restarts), `debug` (what it is doing: spawning, releasing the microphone, a child's exit, its stderr), and `detail` (the verbose log, only while it is on), and exposes `isStarting` and `restarting` beside `isListening` and `isPaused`.

**Where it runs.** The manifest declares `"extensionKind": ["ui"]`: the extension needs the user's microphone, so in a remote window (SSH, WSL, dev containers, Codespaces, tunnels) the editor runs it on the local machine, beside the microphone, rather than on the remote host, which has none. Without the field an extension with only `main` is placed on the remote host. Commands still reach the remote side: `executeCommand` is routed to whichever extension host registered the command, and running a command an unstarted remote extension contributes starts that extension first. The model is read from the extension installed on the local machine (see The bundled model), and the listener lock is the local machine's. The browser editor cannot run a `ui` extension that has no `browser` entry, so there the editor shows it as unavailable and nothing of Wake Word runs. `describeWindow()` in `wakeWordCore.ts` renders `vscode.env.remoteName`, where this extension runs (`context.extension.extensionKind`, which only the editor's `remote.extensionKind` setting can make Workspace), and `vscode.env.uiKind`, for the `Window:` line of Show Diagnostics and the start's `OS:` log line.

sherpa-onnx's keyword spotter applies its own threshold and returns no usable score, so the engine sends `DETECTED:<phrase>` with no suffix and `SherpaEngine` emits the detection with no confidence. Do not reintroduce a placeholder score: a fixed `confidence: 1.00` in the log looked like a real score when it was not. `formatConfidence()` and the calibration averages still handle a score, and render nothing without one.

**Keyword boost and trigger threshold.** `buildKeywordSpec()` ends every keyword line with the fields `:3.0 #<threshold>`, after the pieces, for example `▁HE Y ▁C LA U DE :3.0 #0.05`. `src/keywords.ts` builds the lines, and the host sends them in the config line. sherpa-onnx parses the two fields off the line: `:3.0` is the boost score, which biases decoding toward that phrase's token sequence (1.0 when absent), and `#<threshold>` is the phrase's own trigger threshold. The fields are not part of the keyword the spotter reports on a hit, so `phraseMap` keys and the `details` tokens stay bare pieces.

`wakeWord.confidenceThreshold` is that `#` value. A per-phrase threshold replaces the global `keywordsThreshold` for its phrase, and every line carries one, so the global value (still passed, with the same number) decides nothing; the setting only takes effect through the keyword lines. This was confirmed against the real model with the archive's test WAVs: a line threshold of 0.9 detected nothing whether the global value was 0.05 or 0.9, and 0.05 detected every phrase at a global 0.9. A route may carry a `confidenceThreshold` of its own, and then every line built from that route, aliases included, ends with that value instead of the global one; `buildKeywordSpec()` reads it from the route, so nothing else in the host or the engine has to know the value came from a route. The value is clamped with the same bounds everywhere it is used: `clampThreshold()` in `wakeWordCore.ts`, called in `SherpaEngine.start()` and again inside `buildKeywordSpec()`, once for the global value and once per route with the clamped global value as the fallback, and `clamp_threshold()` in the engine's `config.rs`, so a missing or unusable value writes the global value or the default instead of a line sherpa-onnx cannot parse. The range is 0.01 to 0.9 and the default 0.05 (`MIN_THRESHOLD` and `DEFAULT_THRESHOLD`; `config.rs` repeats the numbers, and the package.json schema must match). The boost and the 0.05 default were tested on Windows with the gigaspeech 3.3M model: before 0.13.2 the lines had no fields and the default was 0.3, and uncommon words such as "claude" in the default phrases were not reliably detected. A user who set 0.3 explicitly keeps it. A change to the setting reaches a running engine: see Settings changes below. The acoustic benchmark builds its list with the same function, and its `--threshold` has the same range and default. `formatDiagnostics()` prints a route's own threshold beside that route, and nothing for a route without one, so a pasted report shows which phrases were listening at which value; `describeThreshold()` gives the `Starting:` and `Calibration: starting` log lines the global value and a count of the routes that replace it, since neither line can name one value for every phrase.

**Default routes.** `DEFAULT_ROUTES` in `extension.ts` has three: Claude (`"hey claude"`, `claude-vscode.focus`, manual handoff), Chat (`"hey chat"` and `"open chat"`, `workbench.action.chat.open`), and Terminal (`"hey computer"` and `"open terminal"`, `workbench.action.terminal.focus`). None of them sets a `confidenceThreshold`, so all three listen at the global value; giving one its own is a tuning decision to make on measurement, not a default. `workbench.action.chat.open` opens the editor's generic chat panel, whichever chat extension is active, so neither the Chat route's label nor its phrases name one. `tests/acoustic/lib/benchmark-core.js` carries a copy of the phrases, pinned by `tests/unit/benchmarkConstants.test.ts`. The README's custom route example uses another extension's command ID as documentation only; it is not a default route. A default route is switched off like any other, without copying the defaults into `wakeWord.routes`: see Switching a route off.

**Routes whose command is missing.** A route whose command is not available in the running editor is set aside: it contributes no keyword lines, so its phrases are never listened for, rather than being detected and then failing with `Could not execute`. The default Claude route is set aside wherever Claude Code is not installed. `checkRouteAvailability()` in `wakeWordCore.ts` decides, from the `CommandSources` the host reads: a command is available when it is registered (`vscode.commands.getCommands()`) or declared by an installed, enabled extension (`vscode.extensions.all`: each manifest's `contributes.commands` and `onCommand:` activation events, read by `manifestCommands()`). The second half is required, not a refinement. `getCommands()` lists only registered commands, and an extension registers its commands when it activates. Running a command that is not registered raises its `onCommand:` activation event, which the editor also raises for every contributed command, so the extension starts and the command runs. Claude Code activates on `onStartupFinished`, as this extension does, in no fixed order, so a check on `getCommands()` alone would set aside the default Claude route on some starts while it works. `vscode.extensions.all` lists enabled extensions only, so a disabled one counts as missing. The editor's own `workbench.*` commands are registered from startup.

The check runs at every start, once the lock is held and before the keyword lines are built. It runs at every resume too, where a changed set means a full start instead of `resume()`, because a command can be registered late with no extension changing. And it runs on `vscode.extensions.onDidChange`, whose change goes through `decideListenSettingsChange()` exactly as a routes change does (see Settings changes), so a route coming back or going never interrupts a handoff. A start reads the commands before anything else, the one wait it has, and then runs to `speechEngine.start()` without another; `listenRequest` is advanced by every start, resume, stop, and calibration run, so one that lands during the read supersedes it, and Disable during the read never opens the microphone. Calibrate applies the same check when it starts the engine, because the engine keeps the routes it was started with and a resume replays them. If the command list cannot be read, every route is listened for.

A set-aside route is a `SetAsideRoute` record held in memory: the route, its label, whether it is a default (by identity with `DEFAULT_ROUTES`), the command, the reason, and the provider where known. The reason is a value of its own, `action-missing`, not a flag on the route, so a route that is off for any other reason is never taken for one whose command is missing, and both can apply at once. The provider comes from the fixed list `KNOWN_PROVIDERS`: `claude-vscode.*` is Claude Code (`anthropic.claude-code`), and `workbench.*` is the editor; any other command is named, with "no installed extension provides" it. `planAvailabilityReport()` decides what to say: an output channel line for each route set aside, each one back, and each one counted as available only through a declaration, compared with the previous check of the session; and a notification only for a route set aside that the user has not been told about. What they were told is kept in global state under `wakeWord.setAsideNotified`, never in settings, which Settings Sync would carry to another machine where the command may be present; the extension never calls `setKeysForSync()`, so that key stays on the machine. A route coming back gets a log line and no notification. A command can still disappear between the check and a detection, and a command that fails when run keeps the existing handling: an error, then listening resumes.

If every route is set aside, no microphone is opened. `waitToListen("commands")` stops the engine, which only matters for a paused one left from a handoff, releases the listener lock, and shows `Wake: No commands`. That tooltip names no route, because it is trusted markdown and route labels and commands are the user's text. The notification says that none of the routes' commands are available and names each one; it follows the same once-per-change rule, except that Enable and a status bar click pass `explicit` and always raise it, since the request would otherwise do nothing visible. While waiting, an extension change or a routes change gets the fifth action of `decideListenSettingsChange()`, `start`, a start that checks again.

**In a remote window the check cannot see the remote host.** `vscode.extensions.all` and `vscode.extensions.onDidChange` cover only the extensions running in the caller's own extension host (`extensionInfo.mine` in the editor's API; the cross-host list is a proposed API that a published extension cannot use). Wake Word runs on the local machine, and an extension with no `extensionKind`, Claude Code among them, runs on the remote host, so its declarations are invisible here and its commands appear only once it has started, or, for one that registers a command only when it is first run, never before that. `readCommandSources()` passes `vscode.env.remoteName` into `CommandSources.remote`, and in a remote window `commandStatus()` counts a command that is neither registered nor declared here as `unverified` rather than `missing`: the route is listened for, `RouteAvailability.unverified` records it, `planAvailabilityReport()` logs a line for it once per session, and Show Diagnostics marks it `not verified`. A missing command then fails when it is run, with the existing handling. The editor's own `workbench.*` commands are the exception: they are registered from startup and visible from every host, so one that is absent is still set aside.

**Switching a route off.** `wakeWord.routesSwitchedOff` lists the routes that are switched off, by label: `["Terminal"]` switches the default Terminal route off and leaves the other defaults coming from the extension, so a default route is switched off without copying the defaults into `wakeWord.routes`, which replaces all of them once it holds one valid route (`resolveRoutes()`). A per-route `enabled` field would need exactly that copy before a default route could be switched off. The setting has no `scope`, like every Wake Word setting, so a workspace value overrides the user value, and the two lists are not merged. `applyRouteSwitches()` in `wakeWordCore.ts` splits the routes `resolveRoutes()` gives into `on` and `off`, comparing labels by `routeKey()`, trimmed and in lower case, so a label written by hand in another case still matches. Labels are required (`isValidRoute()`) but not unique, so one entry switches off every route with that label. A value that is one label rather than a list counts as a list of one, and entries that are not strings or are blank switch nothing off. With nothing switched off, `on` holds every route as the same objects, which `checkRouteAvailability()` identifies the default routes by.

Switched off is a reason of its own, kept apart from set aside. `startListening()` gives `checkRouteAvailability()` the routes switched on only, so a route switched off contributes no keyword lines, its command is not checked, and it is never set aside or told about: switching off the default Claude route where Claude Code is not installed ends that notification, and switching it on again raises it again, because what the user was told is replaced by the routes set aside now. The phrase checks run on the routes listened for, so a route switched off draws no warning or collision, and switching it on reports the checks again (`phraseChecksKey()` changes). An extension change cannot change what is listened for while the route whose command it brings is switched off, so it restarts nothing. The `Starting:` line counts the routes switched off beside those set aside. `planSwitchReport()` logs each route newly switched off and each switched on again, compared with the previous start of the session, so each session's log says which are off; and each label that names no route, once. Such a label is kept, by the setting and by the command: the user settings are shared by every workspace, and the label can name a route that only another workspace defines. Show Diagnostics lists the routes switched off under `Switched off:`, with the settings the value is read from, and each with its command checked (`checkSwitchedOffCommands()`), so a route that is switched off and whose command is missing says both; the section is written only when a route is switched off or a label names none, so a configuration that switches nothing off gives the same report as one without the setting.

If every route is switched off, `waitToListen("routes")` stops the engine and releases the lock as for missing commands, and the status bar shows `Wake: Routes off`, whose click opens the switch command's list. Enable, which passes `explicit`, raises a notification with a button that opens the list; a start nobody asked for raises none, because the user switched the routes off themselves. A change to the routes, the switches, or the extensions while waiting gets `start`, as for missing commands, and `formatListenSettingsChange()` says which wait it ends. When some routes are switched on but none of their commands is available, the state is `No commands`, which describes the routes switched on, and the log line and the notification say that the others are switched off. Calibrate with every route switched off says that it listens for the routes switched on, offers the list, and starts no run.

`wakeWord.switchRoutes`, **Wake Word: Switch Routes On or Off**, shows the routes in a `showQuickPick()` list with `canPickMany`: one entry per label (`routeSwitchItems()`), in the order the routes are configured, with its phrases as the description, checked when it is switched on, and a detail when routes share the label or a route's command is missing, which is checked over every route, switched off or not. The placeholder says which settings the choice is saved in. After the choice the setting is read again and `planRouteSwitchWrite()` decides the write: entries keep their spelling and order, those that name a route now switched on are removed, the labels of routes now switched off that no entry names are added, and everything else stays, including labels that name no route. It writes the workspace settings when they set the value, since a write to the user settings would then change nothing in the window, and the user settings otherwise (`routeSwitchScope()`); it never creates a workspace value, which would replace the user value in that workspace from then on. An empty list is removed from the user settings and kept in the workspace settings, where it still overrides the user value. A choice that changes nothing writes nothing. `wakeWord.routes` is never written. The command logs the value before the write, and the write reaches the engine through the configuration change handler like any edit of the setting.

**SherpaEngine** spawns `bin/wake-word-engine` (`.exe` on Windows) from the installed extension, with no arguments, and sends its config as a JSON line on stdin. Before it spawns, `prepareNativeEngine()` checks that the file exists and, on macOS and Linux, that it is executable, setting mode 755 when it is not: the package records the mode and the editor restores it on install, but an extension unpacked another way can lose it. A binary that is missing, cannot be made executable, or fails to spawn is reported with its path. The binary needs nothing installed: it finds ONNX Runtime and the voice activity model beside itself (see the engine below). The child is started with `windowsHide: true`, so Windows gives the console program no window of its own. The keyword spotting model is in the package as well, under `models/`, and the config line's `modelDir` names that directory: see The bundled model below.

The config line carries `audioDevice`, the `wakeWord.audioDevice` setting, which the engine's `config.rs` resolves to decibri's device selector: a digit-only string is a device index, anything else a case-insensitive name substring, and empty means the system default. A lookup failure is reported by the engine's `mic_errors.rs` with the value and the setting named. The extension builds a new `SherpaEngine` when the setting changes.

The config line also carries `editorName`, `vscode.env.appName`, passed to `SherpaEngine` by `createEngine()`. Microphone permission belongs to the application that started the engine, on macOS the editor that launched it, so `mic_errors.rs` names that editor in the permission message (`Enable microphone access for <editor> in your system privacy settings`), and says "your editor" when the field is absent, as when the binary is run by hand. No editor's name is written into the engine or the extension. The name travels in the config line rather than being added by the extension to the engine's message because the engine composes every capture message from decibri's stable error codes, and the extension has no code to recognise that one message by. `config.rs` replaces control characters in the name with spaces, since it is written into an `ERROR:` line. decibri 6.4.0 declares `PERMISSION_DENIED` but never raises it, so the message is reachable only once the audio backend does; the unit tests in `mic_errors.rs` and `lifecycle.rs` cover it directly.

**Tokenising in the host.** After the model check (`checkModel()`, see The bundled model), and before it spawns, `SherpaEngine.start()` tokenises the routes' phrases. `loadTokeniser()` in `tokeniser.ts` reads the model's `bpe.model` and `tokens.txt`, the one wait after the model check, and keeps the result for the model directory, so a later start or settings change reads nothing. `buildKeywordSpec()` in `keywords.ts` then cleans each phrase up (`cleanUpPhrase()` in `wakeWordCore.ts`), encodes it, and builds the keyword lines and the decoded-to-phrase map, synchronously. The config line carries them as `keywordLines` and `phraseMap`; the engine has no tokeniser and reads nothing else to decide what it listens for. The clean-up rules, in order: upper-case the phrase; remove accents and compatibility forms (decompose with NFKD and drop the combining marks, general category Mn, so a full-width letter becomes its plain letter); read the curly apostrophes U+2018 and U+2019 as `'`; read `. , ! ? : ;` as a space; read any white space as a space, collapse runs of spaces, and trim. What is left must be the letters A to Z, `'`, `-`, and single spaces, the characters the model's pieces spell. A phrase with anything else, a digit among them, cannot be spotted, because the sherpa-onnx library ends the process on a piece it does not have. So it is skipped with a `warning` that names the phrase as configured and the first run of other characters, with "write numbers as words" as the advice, and left out of the lines and the map, so one bad route does not stop the engine. The phrase as configured stays its identity: the warnings, the debug lines, and the phrase map's values (lower-cased and trimmed, which is how a detection finds its route) all name it, and only the keyword line is built from the cleaned-up text. Only when no phrase is left does `start()` emit `No valid phrases to detect`, without spawning; a model the tokeniser cannot read or refuses is `Could not tokenise the wake phrases: <reason>`, also without spawning. A stop or a newer start while the tokeniser loads abandons the start, as during the model check.

**The tokeniser.** `tokeniser.ts` is the extension's own code and runs on the extension host's thread; the extension has no runtime npm dependency. `bpe.model` is a SentencePiece Unigram model despite its name, a protocol buffer: each piece is a length-delimited record of field 1 at the top level, in token table order, holding the piece's text (field 1), its score, a 32-bit float log probability (field 2), and, on the special tokens `<blk>`, `<sos/eos>`, and `<unk>` only, field 3. `parseTokeniser()` refuses a model whose pieces are not the tokens of `tokens.txt` in the same order and count. Only pieces made of A to Z, `'`, `-`, and the boundary marker U+2581 take part, so a special token is never a piece of a phrase. A phrase's pieces are its highest-scoring split (Kudo, "Subword Regularization", ACL 2018, section 3.2), found by a Viterbi search over the whole phrase, each word with the boundary marker in front, under three rules: a candidate's score is the kept score at its start plus the piece's score, in double precision; it replaces the split kept at its end only when it is greater than the score kept there, so an exact tie keeps the earlier start, the longer last piece; and the score kept is rounded to a 32-bit float. Splits whose sums are exactly equal, as in a run of L, F, or P, whose doubled forms are pieces, are decided by that rounding, which depends on the words before, so the search is never run word by word. `tests/unit/tokeniser.test.ts` pins each rule with models built in memory, and a SHA-256 digest of the pieces of every input of the corpus in `tests/unit/tokeniserCorpus.ts`: 835,534 inputs over A to Z, `'`, `-`, and the space, in six categories, so a change to the pieces of any one input fails the test. The pieces are the keyword lines, and the keyword lines are what the spotter detects.

The engine only feeds audio to the keyword spotter while speech is present, so an idle editor does not run the transducer. Chunks wait in a 500 ms pre-roll ring while the detector reports silence and are flushed when speech starts; drop the pre-roll and the onset of the wake phrase never reaches the spotter. Capture is conditioned with DC removal, an 80 Hz high-pass, and AGC targeting -18 dBFS, and delivered as float32, which `samples.rs` clamps to [-1, 1]: AGC can overshoot full scale, and float32, unlike int16, does not saturate. With the verbose log on the engine emits `DEBUG:overruns: <n>` whenever decibri's overrun count has changed, checked every 30 seconds; a rising count means the decode loop is falling behind capture.

**Persistent engine process.** On wake word detection the microphone is released (handoff) and taken back after the cooldown, so only one thing uses the mic at a time. The sherpa child is not torn down for this. `SherpaEngine.pause()` writes `pause`; the child's capture session (`lifecycle.rs`) closes the microphone, resets the VAD gate, replaces the spotter's stream, and prints `PAUSED`, with every model still loaded. The close waits for the microphone's capture thread, which stops once the chunk it is decoding is done: the spotter checks for the close before each chunk, in the lead-in and the segment-end flush as in speech, so a pause that lands during the flush does not wait for the rest of it. `resume()` writes `resume`, and the child opens a new microphone and prints `READY`, which the engine handles exactly like the first one. The pause is acknowledged, not assumed: `pauseChild()` force-kills a child that has not said `PAUSED` within 500 ms, and the next `resume()` starts a new child, as it does when the paused child has died. A child that crashes while paused (`childPaused`) is not retried, because the retry would reopen the microphone during the handoff; a crash while resuming is retried like a crash during a start. `stop()` sends `stop` to a child that has said READY (listening, paused, or resuming) and `releaseThenKill()` waits for `RELEASED`, capped at 500 ms; a child still loading, which reads no commands until the load finishes, is force-killed, and so is every child `dispose()` finds. `stop()` returns a promise that settles once the microphone is closed: `RELEASED`, the cap's kill, or a `start()` or `dispose()` that kills the leaving child first, and at once when no child has said READY. A pause still waiting for `PAUSED` when `stop()` lands ends with that release (`takePauseWait()`), so neither promise says the microphone is closed before it is, and `pause()` on an engine that is not listening returns whichever wait is still in flight, a pause's or a stop's. The extension releases the listener lock on these promises. Both acknowledgements go through `createLineReader()` in `wakeWordCore.ts`, so a verb split across stdout chunks still counts. A settings change during a handoff replaces the paused child through `start()`: the routes or the threshold via `listenSettingsChangedWhilePaused`, the audio device via a new engine.

Commands can reach the child while the microphone is still opening. The capture session has acknowledged a pause or stop that lands then already, so it closes whatever that open produces, and every report from a microphone it has closed is dropped by its id.

**Fatal errors and restarts.** The child reports a fatal error as `ERROR:<message>` and exits 1. Whether a restart can help depends on when it happens, and `SherpaEngine` decides by READY, the engine's own statement that it is listening, with no category in the protocol. `hasListened` is set by READY and cleared by `stop()` and by a final failure, so it covers one listening session, restarts and resumes included. An ERROR before the engine has listened in the session is configuration or environment: no microphone, a device name that matches nothing or several, a device that is not an input, microphone permission, a missing inference runtime or voice activity model, a keyword spotting model that does not load, a config the engine refuses. A new child would fail the same way within the backoff, so `onChildError()` kills the child and `fail()` reports the engine's message once, with no restart. An ERROR once it has listened is the microphone failing under it, a device unplugged, or failing to reopen after a device change; a new child opens whatever device is the default now, so `scheduleRestart()` restarts it after 2, 5, and 10 s, emitting `restarting` with the attempt and the engine's message as the reason, and only when the restarts run out does `fail()` report the last message. A child that ends without an ERROR line, a crash, is restarted in either case, and the final message then says the engine kept stopping, with its exit code. A READY resets the count, and `fail()` gives the next start the full number. A paused child's ERROR, like its crash, is not restarted: the next resume starts a new one. The end of a child is taken from `close`, not `exit`: Node can report the exit before the child's last stdout line has been read, and an ERROR printed just before the exit was otherwise lost and the failure retried as a crash. Because the session spans the handoff, a microphone that goes away during a handoff and cannot be reopened on the resume is restarted, like one unplugged while listening. The rule's cost is a device that is busy for a moment when listening first starts: it is reported rather than retried, and the status bar click retries it.

**Awaited handoff.** `pause()` returns a promise. Listening ends synchronously: `paused` is emitted and any `DETECTED` the child still prints is ignored. The promise settles once the microphone is known to be closed: `PAUSED` arrived, the 500 ms timeout force-killed the child, a `stop()` released it, or the child went some other way (a crash, `dispose()`, a `start()` that replaces it). Every one of those goes through `settlePause()`, reached from `resetChildState()`, or, for a `stop()`, through the release that takes the wait over, so an awaited pause cannot hang, and it never rejects. A second `pause()` while one is waiting returns the same promise. `onWakeWordDetected()` runs the handoff through `releaseThenFire()`: pause, then check the handoff is still current, then `executeCommand`, so the command that hands the microphone to an assistant runs strictly after the release. The currency check is a generation counter. `cancelPendingHandoff()` advances it in `startListening()`, `stopListening()`, `resumeListening()`, and `runCalibration()`, and a Disable or Enable during the release, which settles the release early, therefore abandons the handoff ("Handoff abandoned" in the log) instead of firing the command and starting a cooldown that would turn listening back on. A `wakeWord.audioDevice` change during the release does not abandon it: disposing the old engine settles the release, the command fires, and the new engine starts when the cooldown ends, as for a change made during a cooldown.

**Timing metrics.** With the verbose log on (see below; the Extension Development Host starts with it on) the child logs `Timing: model-load` and `mic-open` when it starts and `resume-mic-open` on each resume; `SherpaEngine` logs `model-check` (reading the model's files and comparing them with their pins, about 0 ms once they have passed in the session), `bpe-load` (reading and parsing the tokeniser's model files, about 0 ms once they have been read for the model directory), and `tokenise` (cleaning up and encoding the phrases and building the keyword lines) before it spawns, and `start-to-ready` (from the `start()` call), `pause-to-ack`, and `resume-to-ready`; `onWakeWordDetected()` logs `detect-to-release`, once the pause has settled, and `detect-to-command`, measured until the command's promise settles. They are written at the debug level. Nothing is timed while the verbose log is off.

**The verbose log.** The output channel is a `LogOutputChannel` (`createOutputChannel("Wake Word", { log: true })`), so the editor's own log levels apply to it: **Developer: Set Log Level**, then Wake Word, or the level control in the Output panel. The editor writes the time and the level on each line, and keeps the channel's log file in its logs folder. At Info, the default, the channel has what it has always had. At Debug or Trace (`isVerboseLogLevel()`) the verbose log is on: `SherpaEngine` sends its `detail` events (the timing lines, each phrase's pieces, the model check) and the engine its `DEBUG:` lines (the load, the microphone opening, voice activity transitions, each keyword result, overruns), all written with `outputChannel.debug()`. `onDidChangeLogLevel` calls `applyVerboseLog()`, which calls `ISpeechEngine.setDebugMode()`: `SherpaEngine` starts or stops its own detail at once and writes `debug on` or `debug off` to a child that is running, paused, or loading, which flips the engine's `DebugSwitch` (`protocol.rs`). The reporter and every capture thread share that switch, and a capture thread drops its debug reports at the source while it is off, so the change reaches a microphone that is already open, with no restart, no reload, and a handoff undisturbed; the engine says `DEBUG:debug lines on` when it goes on. A child spawned later, by a start, a restart, or a resume that needs a new one, gets the mode in its config line's `debugMode`, read when it spawns rather than when the start began. The level the channel starts at can be one the user set earlier, which the editor applies just after the channel is made; the change event covers that too. `.vscode/launch.json` passes `--log=analytics-in-motion.wake-word:debug`, so the Extension Development Host starts with the verbose log on.

Nothing in the verbose log is audio or a transcript. The keyword spotter can only complete one of the configured keywords, and the engine says nothing about a decode step that completes none (`spotter.rs` pins that, over a whole segment and its flush); a hit is written as the spotter's result for that keyword, its tokens and timestamps. The other lines are fixed text, counts, timings, paths, and the configured phrases. No sample value is ever formatted. `log()` and `logDetail()` pass every line through `redactHome()`, as Show Diagnostics does, because a log is pasted into an issue as often as the report is.

**The toggle shortcut.** `package.json` binds `wakeWord.toggle` to Shift+Alt+W on Windows and Linux and Ctrl+Cmd+W on macOS, with no `when` clause, so it works wherever focus is: an editor, a panel, a webview such as an assistant's panel (webviews forward every keydown to the workbench's keybinding dispatch), or the terminal. A foot pedal that sends a key combination can send it, which gives a hands-free resume after a manual handoff. Both combinations are unbound in the default keybindings of VS Code 1.85, 1.128, and 1.138 on their platform, and in the editors built on them that were checked, including their own additions and those of the Claude Code extension, and none of Windows, macOS, GNOME, or KDE reserves them. On Windows and Linux, Ctrl+Alt with a letter is AltGr on many keyboard layouts and types a character, so the shortcut avoids it; Shift with the left Alt types nothing. On macOS, Option with a letter types a character, which would reach a webview's text box as well as the shortcut, so the shortcut uses Command and Control, neither of which types. `tests/unit/manifest.test.ts` pins the binding.

While the integrated terminal has focus, it passes a key to an editor command only when the command is in `terminal.integrated.commandsToSkipShell`, or, on macOS, when the key uses Command; anything else goes to the shell. `contributes.configurationDefaults` therefore puts `wakeWord.toggle` in that setting's default. A value the user has set replaces the default, and when another extension also contributes a default for that setting, the editor keeps one of the two lists, not both, since it merges only object defaults. In either case the shortcut goes to the shell while the terminal has focus, and Show Diagnostics' `Toggle shortcut in the terminal:` line says so (`terminalHandsOverToggle()`); adding `wakeWord.toggle` to the setting fixes it.

**Handoff modes.** Each route's `handoff` field, resolved by `resolveHandoff()` in `wakeWordCore.ts`, decides how listening comes back after the route fires. `timer`, the default and the only behaviour before 0.11.0, is the cooldown countdown above. `manual` calls `enterManualPause()`: no timer, the status bar shows `Wake: Paused`, and the `isManuallyPaused` flag makes the status bar click and the Enable command call `resumeListening()` instead of stopping or starting. The Enable command also resumes early during a timer cooldown: before 0.13.0 it called `startListening()` there, which reopened the microphone while the countdown kept running and left the status bar on the countdown. `stopListening()`, `resumeListening()`, and `startCountdown()` clear the flag. An engine rebuild during a manual pause builds the new engine but does not start it; the user's resume does. A `wakeWord.routes`, `wakeWord.routesSwitchedOff`, or `wakeWord.confidenceThreshold` change during any handoff pause sets `listenSettingsChangedWhilePaused`, and `resumeListening()` then goes through `startListening()` rather than `resume()`, which would replay the settings the child was paused with. Regaining focus after a `pauseOnFocusLoss` pause resumes through `resumeListening()` as well, so a change made while the window was unfocused is applied there too. With that setting on, a cooldown that ends while the window is not focused does not resume: the window waits for focus, and the lock, kept through the handoff, goes to the focused window. See Settings changes below. Anything other than the exact string `manual` is `timer`, because settings.json is not validated against the schema. The default Claude route is manual; Chat and Terminal are timer.

**Settings changes.** `onDidChangeConfiguration` acts on five settings; every other one is read where it is used and needs nothing here. `wakeWord.audioDevice` rebuilds the engine, which is built with the microphone it listens on: the branch disposes of the old engine, settles a calibration run, writes the session counters out, and starts the new engine only if the old one was listening or on its way to listening (starting or restarting), so a rebuild during a cooldown or a manual handoff waits for the resume, and a window waiting for focus goes on waiting and starts the new engine when it is focused. Because every path out of it ends in a start, which reads the settings again, a routes, switches, or threshold change in the same event needs nothing of its own and the branch returns. `wakeWord.pauseOnFocusLoss` calls `applyFocusSetting()`, in that branch as well: see Multi-window coordination.

`wakeWord.routes`, `wakeWord.routesSwitchedOff`, and `wakeWord.confidenceThreshold` are the settings a running engine cannot pick up on its own: `startListening()` reads all three and sends them in the config line, the routes switched on as `keywordLines` and the threshold as `threshold`. They are handled identically, by `decideListenSettingsChange()` in `wakeWordCore.ts`, which takes what changed and what the extension is doing and returns one of five actions: `restart` while the engine is listening, which is `stopListening()` then `startListening()`; `apply-on-resume` while it is paused, for a cooldown, a manual handoff, or a focus-loss pause, which sets `listenSettingsChangedWhilePaused`; `apply-when-started` while a start is in flight, which sets `listenSettingsChangedWhileStarting` and is consumed by the `started` handler (in flight means `engineStarting`, set by a start and by a resume from the moment it begins, or a restart after the engine stopped on its own, whose child replays the old settings); `start` while waiting because no route's command is available or every route is switched off (see Routes whose command is missing and Switching a route off); and `none` when the extension is off, in the error state, or standing by while another window listens, since the next start reads the settings itself. A change to `wakeWord.routesSwitchedOff` is a kind of change of its own, `switches`, so the log line names it, and a change in which routes' commands are available, found on an extension change, is another, `availability`; both are handled identically. The rule the decision exists for is that no paused state may start or restart the engine, because paused means a handoff and a handoff means an assistant has the microphone; the tests assert that over every combination of the state flags. `startListening()` clears both deferral flags once it has read the settings, rather than the resume clearing them before its start, so a second resume landing while the first start reads the commands cannot replay the old settings through `resume()`. A start in flight is checked before the paused flags, because a resume through `startListening()` leaves the engine paused until READY and the resume that would have consumed a deferral has already happened. The `apply-when-started` case is what makes the Settings editor's several writes for one edited number end at the value the user typed: each write restarts, the last one wins, and the cost is one model load per write. `formatListenSettingsChange()` writes the log line, which names the settings that changed and when the change will be applied.

A change during a calibration run reaches the engine the way any change does: the run is listening, so the engine restarts and `stopListening()` settles the run as `stopped`, which reports nothing and restores nothing. A change that lands while Calibrate is still starting its engine is held if that engine is paused (Calibrate starts it directly, so `engineStarting` is not set) and otherwise waits for the next start.

**Calibration.** `wakeWord.calibrate` runs `runCalibration()`. It records what the extension is doing (`capturePriorState()`), starts the engine if it is not listening and waits for `started`, then keeps a `CalibrationRun` in module state for `CALIBRATION_DURATION_MS` (15 s). `onWakeWordDetected()` checks that state right after the debounce guard and, while a run is active, records the detection and returns without firing a route or applying confirmation mode. `formatCalibrationReport()` in `wakeWordCore.ts` renders the log lines and the notification text. Afterwards `restorePriorState()` puts things back: listening and a pause for focus come back as the focus handler would decide them now, since a run ignores focus changes (a pause for focus if the window is not focused and `pauseOnFocusLoss` is on, listening otherwise), an interrupted cooldown restarts its remaining seconds through `startCountdown()` (which, unlike `scheduleResume()`, does not count a cooldown), a manual handoff stays paused, and Off stops the engine and releases the listener lock. A run ends on its timer, on the notification's Cancel, on a status bar click, on `stopListening()` or an engine rebuild (outcome `stopped`: nothing is reported or restored), or on an engine error. Calibration refuses to run without consent, while another window holds the lock, and while every route is switched off. An engine it starts is started for the routes switched on whose commands are available; with none, the run ends as `no-commands` before anything starts, and the user is told why. It starts the engine through `ISpeechEngine.start()` directly, not `startListening()`, so the "Starting:" log line is not written for a calibration start.

The engine cancels a pending crash-backoff retry in `stop()`, `pause()`, and `start()`. `stop()` is the privacy case (Disable must disable); `pause()` during backoff leaves the engine paused with no process so `resume()` restarts it; `start()` during backoff supersedes the retry rather than letting it fire into the fresh child. `stop()` also kills the child before its state guard: between spawn and `READY` the engine is neither listening nor paused, and an early return there left the child to finish starting and open the microphone after a Disable.

**Multi-window coordination.** Every editor window runs its own extension host and each one activates this extension, so without coordination three windows meant three engine processes on one microphone. `lockFile.ts` implements a PID lock at `<globalStorage>/wake-word.lock`. A window opens the microphone only while it holds the lock, and gives the lock up only once its microphone is closed: `releaseLockWhenClosed()` waits for the promise the engine's `pause()` or `stop()` returns, and releases the lock then only if `needsListenerLock()` in `wakeWordCore.ts` says nothing in the window needs it any more (a start or a resume can have begun meanwhile). A window that takes the lock therefore never finds the microphone still open in another one. `deactivate()` kills the engine's child with `dispose()` and releases the lock at once, since the extension host is going away. Which window holds the lock depends on `wakeWord.pauseOnFocusLoss`, which is on by default.

**With the setting on, listening follows focus.** The window learns of focus from `vscode.window.onDidChangeWindowState`, and reads `vscode.window.state.focused` at activation. Both follow the operating system's focus of the editor window and of its floating editor windows: the workbench forwards `document.hasFocus()` over them, latched, in 1.85 as in later releases. Moving between the editor, the terminal, panels, and webviews such as an assistant's panel inside one window does not change it; another application, another editor window, and a dialog of the operating system's own do. A window that loses focus does what `decideFocusLoss()` says. A handoff (the release, a cooldown, or a manual pause) and a calibration run keep the lock. An engine that is listening, or restarting after a crash, is paused, which also calls off a restart not yet begun, and the lock goes once the microphone is closed. A start or a resume under way cannot be paused, so the `started` handler pauses it as soon as it is listening, and it keeps the lock until then. A window standing by stops checking. A window whose engine failed, or is off, releases the lock at once. `pauseForFocus()` does the pausing, and every way into the paused-for-focus state goes through it: losing focus, a start (`startListening()`) or a resume (`resumeListening()`, at the end of a cooldown, after a manual handoff, or after a lock takeover) in a window that is not focused, READY in such a window, and Calibrate putting a focus pause back. The editor windows restored at startup therefore all run Enable, and only the focused one starts its engine; the others show `Wake: Unfocused` and load nothing until they are focused. Gaining focus ends the pause through `resumeListening()`, which takes the lock first. If the window that lost focus has not released it yet, this one stands by (`standBy()`), shows `Wake: Other window`, and `startLockWatcher()` checks every `LOCK_HANDOVER_INTERVAL_MS` (100 ms) for `LOCK_HANDOVER_MS` (2 s) and then every `LOCK_FOCUSED_CHECK_INTERVAL_MS` (1 s) while it stays focused (`lockCheckDelay()`, counting the wait from its own delays); when it gets the lock it resumes its paused engine, or starts one. A window never takes a lock held by a live window, so it waits as long as the other holds it: milliseconds for a pause, 500 ms at most (the engine's pause timeout), the rest of a start, or the whole of a handoff. A window that is not focused never takes the lock. There is no delay before a focus pause: it would keep the microphone open in a window the user has left and delay every handover by as much, and a pause and a resume cost only a device close and open, since the engine keeps its model loaded: measured with the packaged engine on Windows, a median of 3 ms to PAUSED and 77 ms to READY, against 876 ms for a start with the model load. A pause for focus ends when the window is focused again even if the setting was turned off meanwhile; turning the setting on in a window that is not focused acts as the window losing focus (`applyFocusSetting()`).

**With the setting off**, the lock behaves as it always has. `startListening()` takes the lock before starting the engine; a window that cannot take it shows "Wake: Other window" and checks every `LOCK_CHECK_INTERVAL_MS` (10 s) until the holder's PID is gone or the file is removed, then starts. The lock is held across pause and cooldown, released by `stopListening()` (Disable, toggle off, consent reset, deactivate) once the microphone is closed, and taken over when its PID is dead or the file is corrupt.

**The lock file.** Creation uses the `wx` flag so windows that start at the same moment cannot both win. Three more races, each of which would let two windows believe they hold the lock at once, are closed in `tryAcquireLock()`: a corrupt lock written less than `LOCK_WRITE_GRACE_MS` (1 s) ago is one still being written, since the exclusive create makes the file before the write fills it, and is left alone; only the window that creates the takeover file (`wake-word.lock.takeover`) exclusively deletes an abandoned lock, and it reads the lock again first, so two windows taking over one stale lock cannot delete each other's new one; and a create that fails for another reason than EEXIST is a failure to take the lock this time if a probe file beside it (`wake-word.lock.<pid>.probe`) can be written, since Windows can refuse a name for a moment while another process deletes the file that had it. Only a storage directory that cannot be written at all makes the extension listen without coordination. `describeLock()` renders the lock state for diagnostics. Known limits: different editor products have separate global storage and do not see each other's lock, so with the setting off a window of each can listen at once (with it on, only the focused one listens, as only one window has focus); a window in the error state keeps the lock while it is focused, or with the setting off until listening is disabled there or it closes; PID reuse after a crash can make a stale lock read as live until that process exits; and a takeover file left by a window that crashed in the microseconds of a takeover delays the next takeover by up to a second.

**Consent from another window.** Consent is global state, which the editor shares between windows and updates in each, so it can be reset in another window while this one is paused. `startListening()` and `resumeListening()` check it (`consentWithdrawn()`): a start or a resume after a reset turns listening off with a log line instead, and Enable asks again.

**Session statistics.** `extension.ts` keeps a `SessionStats` record (defined in `wakeWordCore.ts`): detections per route label, errors, engine starts, cooldowns, and a start time. `formatSessionStats()` renders it as one log line, written on deactivate and before an engine rebuild resets the counters, and included in the diagnostics report. No storage, no network.

**Phrase confirmation.** `wakeWord.confirmationMode` (off by default) makes `onWakeWordDetected()` hold the first hearing of a phrase instead of firing. `evaluateConfirmation()` in `wakeWordCore.ts` makes the decision; the extension keeps the engine listening, shows `Wake: Confirm "<label>"` in the status bar, and starts a `CONFIRMATION_WINDOW_MS` (5 s) timer. The same label heard again inside the window fires the route as normal. A different label replaces the hold and restarts the timer. The timer expiring drops the hold and puts the status bar back to Listening, provided the engine is still listening. The debounce guard runs before the confirmation check so an engine re-firing on one utterance cannot confirm itself, which also means the second utterance has to land between `DETECTION_DEBOUNCE_MS` (3 s) and 5 s after the first. `clearConfirmation()` drops the hold in `stopListening()`, the focus-loss pause, `resumeListening()`, and the engine rebuild handler. Session statistics count a detection only once it fires.

**Phrase checks.** `startListening()` calls `reportPhraseChecks()` once it holds the lock, just before the engine starts, for the routes listened for: a set-aside route, or one switched off, draws no warning or collision for phrases that cannot fire, and when it comes back or is switched on the checks are reported again, because `phraseChecksKey()` changes. `validatePhraseQuality()` warns about a single word, a phrase under `SHORT_PHRASE_LENGTH` (4) characters, and a word from `COMMON_WORDS` on its own; one phrase can draw all three. `detectPhraseCollisions()` flags the same phrase on two routes (only the first can fire: `matchRoute()` takes the first match), two phrases that differ only in case, punctuation, accents, full-width forms, or white space (one keyword line, so only one of the two routes can fire), and a phrase contained in another route's phrase, by plain substring. Routes are compared by position, not label, and aliases on one route are never compared with each other. Both work on normalised phrases, so they skip what the engine skips, and judge each as the spotter hears it, its cleaned-up text, while their lines name it as configured: "Hey!" draws the common-word warning. `formatPhraseChecks()` renders one warn line each and a single notification points at them. The report is repeated only when `phraseChecksKey()` (each route's label and normalised phrases) differs from the last one reported, so resumes, restarts, and lock takeovers stay quiet, and so does editing a command or cooldown. Nothing is ever blocked.

**Diagnostics.** `wakeWord.diagnostics` runs `runDiagnostics()`, which gathers the report and hands it to `formatDiagnostics()` in `wakeWordCore.ts`. It runs the packaged binary's self-test with `probeNativeEngine()` (5 s timeout, never rejects; the `Engine binary:` line carries what it printed, or `missing`), checks the bundled model's files with `checkModel()` (see The bundled model), reads the lock with `readLock()`/`describeLock()`, describes the extension's state with `describeState()`, which is `describeStatus()` of the state the status bar shows, gives the window's context in a `Window:` line (`describeWindow()`: local, or the remote's name and where Wake Word runs), and checks the routes' commands afresh: the routes listened for are listed under `Routes:`, a route listened for unverified in a remote window marked `not verified`, and the routes set aside under `Set aside:`, each with its reason and what provides its command, then the routes switched off under `Switched off:`, written only when a route is switched off or a label names none (see Switching a route off). It lists the input devices (see Input devices), and gives the log level with whether the verbose log is on, and whether the terminal hands the toggle shortcut over. `formatDiagnostics()` passes every line through `redactHome()`, which replaces the home directory with `~` (whole path segments only; case-insensitive on Windows), because the report is meant to be pasted into a public issue. The lines are logged, and the notification offers Show Log, Copy to Clipboard, or Report Issue. No audio and no network.

**Input devices.** `wake-word-engine --list-devices` prints the input devices on one line and exits, without reading stdin: `DEVICES:` then a JSON array with one object per device, in decibri's order, each with `index`, `name`, `id`, `default`, `channels`, and `sampleRate` (`engine-rs/src/devices.rs` and `engine-rs/README.md` document the format). No devices is `DEVICES:[]`, and a failure is `ERROR:<message>` with exit code 1. decibri's `input_devices()` enumerates and reads each device's default format, so no stream is opened, and neither ONNX Runtime nor a model is loaded. Fields are only added, never renamed, so a device picker can read the same line. `listInputDevices()` in `sherpaEngine.ts` runs it for Show Diagnostics (5 s timeout, never rejects) and `parseDeviceListing()` reads it; a failure is one `Input devices: could not be listed (<reason>)` line and the rest of the report goes on. `selectDevice()` decides which device `wakeWord.audioDevice` selects the way the engine does, `resolve_audio_device()` in `config.rs` and then decibri's lookup: empty is the system default, digits only are an index, and anything else is a case-insensitive substring of the name, where one match opens and none or several open nothing. `formatDeviceLines()` marks the system default and the selected device, and says when the setting selects none. The platform's `id` is not in the report: it identifies a particular device.

A device can be named after a person, as operating systems name a Bluetooth headset or a phone after its owner. The report is pasted into a public issue, so `redactDeviceName()` replaces the owner in the forms operating systems use, "Ann's Headphones" (a straight or curly apostrophe, and "James' ...") and "Headphones de Ann" / "von" / "van" / "di", and the login name and the home directory's last segment wherever they stand alone, with `<name>`, and keeps the rest, because the kind of device is what diagnosing needs: a headset, a built-in array, a Bluetooth device in its 16 kHz hands-free mode. The `wakeWord.audioDevice` value is treated the same. A name in another form gets through, so the report's `Input devices:` line says that names that look like a person's are shown as `<name>` and to check the names before posting. A capitalised word after "de" or "di" that is not a name is replaced too; the index and the format still identify the device.

**Reporting an issue.** Show Diagnostics' Report Issue puts the report on the clipboard in a fenced block (`issueReportText()`) and opens the new-issue page of the repository in `package.json`'s `bugs.url` (`issueReportUrl()`), with `ISSUE_BODY`: headings, and a comment asking for the report to be pasted and read before submitting. Nothing is sent: the address carries only that fixed text, not the report, because a browser sends the address to the site as soon as it opens the page, and the user pastes, reads, edits, and submits the report themselves, or does not. `vscode.env.openExternal()` takes a Uri, whose query the editor decodes and encodes again, so `ISSUE_BODY` holds none of `? # & = + %`, which a test pins. The editor's own issue reporter is not used: an extension contributes to it only through a proposed API, and an editor built on VS Code can route that reporter elsewhere.

**The engine (`engine-rs/`).** `engine-rs/` is the engine child process, a Rust binary that needs nothing installed on the user's machine. It handles a `pause` or `stop` that lands while the model is loading or the microphone is opening, and writes `DETECTED:<phrase>` for the configured phrases. It captures audio through the `decibri` crate (pinned `=6.4.0`, features `capture`, `vad`, `gain`, `ort-load-dynamic`) and gates it with decibri's Silero VAD at a 0.5 threshold; the capture loop scores each chunk before gating it, so the chunk that trips the detector is not stranded behind the gate. ONNX Runtime (1.28 or later) and `silero_vad.onnx` are loaded at run time for the VAD, from `ortLibraryPath` and `vadModelPath` in the config, the `ORT_DYLIB_PATH` and `WAKE_WORD_VAD_MODEL` environment variables, or files beside the executable; `--self-test` reports which it found, and the version the linked sherpa-onnx library reports, without opening a microphone and without loading the keyword spotting model. It does load the voice activity model, which is why the self-test fails on a machine missing the inference runtime's own dependencies. CI builds the binary and every platform `.vsix` carries it in `bin/`, beside ONNX Runtime and `silero_vad.onnx`, where it finds both with no configuration (see Boundaries for how it is built and checked); `engine-rs/**`, the source, is excluded from the `.vsix` by `.vscodeignore`, and `engine-rs/target/` and `bin/` are gitignored. `engine-rs/README.md` has the protocol, the build commands, and how to point a local build at ONNX Runtime and the models.

Keyword spotting is the `sherpa-onnx` crate, pinned `=1.13.8`, with the `static` feature: the crate's build script unpacks prebuilt static libraries for the target into `engine-rs/target/sherpa-onnx-prebuilt/` (the release build hands it the pinned archives described below), and they carry their own ONNX Runtime, which is linked into the executable and is separate from the one decibri loads for the VAD. On Windows those libraries use the static C runtime, so `engine-rs/.cargo/config.toml` sets `+crt-static`; build from inside `engine-rs/` or that file is not read. `spotter_config()` in `spotter.rs` is pinned field for field by a unit test, `modeling_unit` and `bpe_vocab` included, although the keyword spotter uses neither: it creates a spotter with `bpe_vocab` naming an empty file or no file, so the engine does not require `bpe.model`. The engine has no tokeniser. It takes `keywordLines` and `phraseMap` from the config line, refuses a config without either (`Startup error:`) or with no lines (`No valid phrases to detect`) before anything loads, and passes the lines in memory. Before the model loads, `check_keyword_lines()` checks every line the way the library parses it: each word, split where C's `isspace()` splits, must be a token in `tokens.txt` or a `:` or `#` field whose number `std::stof` can read. The library does not report a bad line as an error: it ends the process on an unknown token (exit -1, with the reason only on stderr), and a field it cannot read throws a C++ exception across the FFI boundary that aborts the process. A NUL cannot pass the bindings' C string, a line break would make one entry two lines, and a line with no pieces names no keyword. The special tokens `<blk>`, `<sos/eos>`, and `<unk>` are in `tokens.txt` but spell no part of a word, so a line that names one is refused as well (`SPECIAL_TOKENS` in `spotter.rs`). The engine refuses each of these as `Failed to load KWS model:`, naming the phrase or the line. The extension already leaves unspottable phrases out; the check is there for any line that arrives anyway. The stream is reset after a detection and at the end of each speech segment, and replaced on `pause`.

**Archives without text-to-speech.** The official sherpa-onnx archives also carry the text-to-speech components, which the engine never calls. `.github/workflows/engine-archives.yml`, run by hand with an upstream release tag, builds the same libraries for the four targets with `SHERPA_ONNX_ENABLE_TTS=OFF` (`engine-rs/archives/build.sh`), under the official archives' names and `<name>/lib` layout so that the `sherpa-onnx-sys` build script uses them unmodified, and uploads each one after `engine-rs/archives/verify.mjs` has checked it against the official archive for the same release and target. The build script links `espeak-ng`, `piper_phonemize` and `ucd` by name and a build without text-to-speech does not produce them, so each archive carries them as libraries holding one empty object file; the link list has no whole-archive modifier, so nothing is linked from them. Otherwise the build matches the official archives: the static C runtime on Windows, a universal build thinned to arm64 for macOS 11.0, and Linux inside the engine's `manylinux_2_28` image, compiled by GCC 11 (`gcc-toolset-11`, which `build.sh` installs there) for the `std::string` ABI of the ONNX Runtime the archive carries: pre-C++11 on x64, C++11 on aarch64. `pinned-inputs.mjs` pins the archives it built for sherpa-onnx 1.13.8, hosted on this repository's `sherpa-onnx-v1.13.8` release: `prebuilt.mjs` downloads them from there, and `SHERPA_ONNX_ARCHIVE_DIR` hands them to the build script, whose own download is the official archive. `engine-rs/archives/README.md` says how to run it and what it checks. A target directory keeps linking the libraries its last `sherpa-onnx-sys` build used: the build script runs again only when `SHERPA_ONNX_ARCHIVE_DIR` or `SHERPA_ONNX_LIB_DIR` changes, and the libraries are copied into that crate's build output. Deleting `engine-rs/target/sherpa-onnx-prebuilt/` alone does not change what the next build links; to switch archives, also run `cargo clean -p sherpa-onnx-sys`, or build with an empty `CARGO_TARGET_DIR`.

On Windows the native library opens the model files through C runtime calls that refuse a path of 260 characters or more: it reports `transducer encoder: '<path>' does not exist` on stderr, although the engine's own check finds the file (a 259-character path loads and a 260-character one does not). The model is in the user's global storage, so a long account name or a redirected profile is enough. `library_model_dir()` in `spotter.rs` therefore canonicalises the model directory before it goes into the spotter configuration, which on Windows yields the verbatim form starting `\\?\`, exempt from the limit; a directory that cannot be canonicalised, and every directory on other platforms, is passed as given. Paths of 260 to 1,000 characters, with and without non-ASCII characters and forward slashes, load this way, and the drive script loads the model from a path over 300 characters on every platform. The fix is in the engine, not the host, because the limit belongs to the library: the host passes the model directory as the editor's global storage spells it. A short (8.3) path also loads but exists only where the volume generates short names, and a link at a short path would give the host a second location to manage.

Three timing details decide whether a phrase said on its own is detected, and each is pinned by tests because they are easy to break. The spotter decodes in 320 ms steps counted from the first sample it is given, and reports a keyword only once a step has covered the phrase's last piece and the blank after it. So (1) `Spotter::end_segment` finishes that decoding before it resets the stream: it feeds the stream `SEGMENT_FLUSH_MS` of silence, 1,600 ms as sixteen chunks, and drains it, so the step covering the end of the phrase is decoded rather than discarded, and a phrase the search is still resolving has audio after it to settle on. Measured over 1,448 phrase opportunities in 92 minutes of synthesised speech: 67.5% of them detected with no flush, 80.3% at 320 ms, which is the first step, 81.6% at 1,600 ms, and no more at 2,400 ms, 3,200 ms or 4,800 ms; "hey claude", the longest piece sequence of the default phrases, went from 25.8% to 60.2%, and the further steps beyond the first are worth 1.2 points, every one of them a phrase heard in noise. The one false positive in the 14 minutes of speech that contains no phrase is the same clip at every length, including no flush, and the median delay from the end of speech to the detection went from 352 ms to 380 ms. The flush is five decode steps of work on the capture thread, tens of milliseconds on a fast core and over a hundred on a slow or power-throttled one, and it stops early in two cases. A keyword completing inside it ends it there, since the search has just started again and the extension answers a detection with a pause, which replaces the stream. The stream is owed the rest (`Spotter::flush_owed`): one that is fed anything before a pause replaces it, as when a detection is held for confirmation, gets the rest first, so it decodes later audio exactly as after the whole flush, and over the 1,388 clips above the detections, phrase and chunk, are the same as with a flush that always runs to the end. A close ends it too: `SpeechSink` takes a `closing` check, which the spotter makes before each chunk it decodes, so a pause or a stop waits for the chunk in hand rather than the rest of the flush. A phrase the rest of the flush would complete after a close has begun could not be reported in any case, because the capture session drops every report from a microphone it is closing. The flush belongs to the segment end alone: a pause replaces the stream instead, because a detection from audio heard before the microphone was handed over must not arrive after it, and a segment end that lands after a pause therefore flushes a stream that has heard nothing. (2) The silence holdoff in `hysteresis.rs` runs from the arrival of the first quiet chunk, its end, not its start, which with 100 ms chunks puts four quiet chunks into the spotter before the reset. (3) The lead-in handed to the spotter when speech starts is five chunks counting the chunk that trips the detector, so the ring holds four. Both (2) and (3) move every decode step, and before the flush existed each was worth several points; with it, one chunk either way is worth 0.4 points or less on that clip set, and what the tail now decides is how soon a detection is reported: a segment that ends one chunk sooner reports its phrase about 40 ms sooner at the same detection rate.

With the verbose log on the engine times `model-load` (the keyword line check and the transducer), `mic-open`, and `resume-mic-open`; the host times the tokenising. `cargo test` needs no model and no microphone. `engine-rs/scripts/drive-protocol.mjs` drives the built binary over a real pipe, with `WAKE_WORD_MODEL_DIR` pointing at the model for the scenarios that load it: the repository's `models/<name>/`, or the copy `scripts/fetch-model.mjs` makes of it.

**The status bar.** The rule: it never says Listening unless the microphone is open, and never says the microphone was handed to an assistant unless a wake phrase handed it over. Nothing sets a status bar state directly. `refreshStatusBar()` in `extension.ts` gathers `StatusFacts` (`statusFacts()`: the engine's `isListening`, `isStarting`, and `restarting`, and the extension's own flags: `handingOff`, the countdown, `isManuallyPaused`, `isPausedByFocus`, `engineStarting`, `engineFailure`, the lock watcher, `waitingFor` as two facts, waiting for a command and every route switched off, the calibration run, the held confirmation), `deriveStatus()` in `wakeWordCore.ts` picks the state, and `statusBarView()` gives its text, tooltip, colour, and whether the tooltip carries the settings link. Code that changes a fact calls `refreshStatusBar()` afterwards. The states: `Off`, `Starting` (from the moment a start or a resume asks the engine to start, through the model check, the tokenising, the model load, and the microphone opening, until READY), `Listening`, `Confirm "<label>"`, `Calibrating`, `Active` (a detection releasing the microphone and running the route's command), the cooldown's `<n>s`, `Paused` (a manual handoff), `Unfocused` (paused while the window is not focused, with `pauseOnFocusLoss`), `Restarting` (the engine stopped on its own and is being restarted; the tooltip gives the attempt), `Error` (the tooltip gives the engine's message), `Other window` (another window has the lock; with `pauseOnFocusLoss` on, the tooltip says this window listens as soon as that one releases the microphone, and a click turns listening off here, so the fact carries the setting), `No commands`, and `Routes off` (every route is switched off). `deriveStatus()` reaches the listening states only through `listening`, which follows the engine's READY, and the handoff states only through the facts a detection's handoff sets, so an engine paused for focus, which `SherpaEngine` reports with the same `paused` event as a handoff, can never read as a handoff; a restart ranks above a start, a start above a focus pause, and all of them above an earlier error. A pause for focus ends when the window is focused again, even if `pauseOnFocusLoss` was turned off meanwhile, because nothing else would end it and the `Unfocused` tooltip says so. Off, `Unfocused`, `Other window`, `No commands`, and `Routes off` show `$(circle-slash)`: `mic-off` is a recent icon, which an editor built on an older VS Code release does not have and draws as nothing, and the view test pins every state's icon to ones such editors have. A click on the status bar turns listening off in every state where it is on or on its way (`listeningWanted()`: listening, handed off, paused, paused for focus, starting, restarting, or standing by for the lock while listening follows focus), resumes a manual handoff, cancels a calibration run, opens the switch command's list in `Routes off`, and otherwise starts listening; Enable during a start does nothing. Show Diagnostics' `State:` line is `describeStatus()` of the same state. A tooltip with the settings link is trusted markdown, so no state whose tooltip carries a route label or an engine message has one. `tests/unit/statusBar.test.ts` checks every state's view and `deriveStatus()` over all 8,192 combinations of the facts.

**Open Settings.** `wakeWord.openSettings` opens the Settings editor filtered to `wakeWord`. The Off and Listening status bar tooltips are trusted `MarkdownString`s ending in a command link to it; the status bar click itself stays the toggle.

**The bundled model.** The keyword spotting model ships in the package, so listening needs no download and no network access. `KWS_MODEL` in `speechModel.ts` names it, `sherpa-onnx-kws-zipformer-gigaspeech-3.3M-2024-01-01`, and lists its five files with each one's size and SHA-256: the three int8 networks and `tokens.txt`, which the engine loads, and `bpe.model`, which the tokeniser reads. The files are committed under `models/<name>/`, byte for byte those of the publisher's archive, and `.gitattributes` marks `models/` binary, because `tokens.txt` is text and a checkout that converted its line endings would change its digest. The package carries the directory at the same path, so no `.vscodeignore` line may exclude it. `modelDirectory()` gives its place in an installed extension: `SherpaEngine` passes it the directory above `dist/`, the root it finds `bin/` in, and Show Diagnostics passes the extension's path. Everything that names the model's files reads them from `KWS_MODEL`: the start, Show Diagnostics, `scripts/verify-vsix.mjs`, `scripts/fetch-model.mjs`, and the tests. The benchmark keeps a copy, pinned by `tests/unit/benchmarkConstants.test.ts`. A second model would be a second `SpeechModel`, with a directory of its own under `models/`. Changing the model means replacing the files and their pins together; the drive script's `MODEL_FILES` and its keyword lines name the files and pieces of this one.

`checkModel()` reads every file of the model and compares its size and SHA-256 with the pin, before the first start of a session: about 5.5 MB, timed as `model-check` in the verbose log. A directory that passes is not read again in the session; a check that finds a problem is not kept, so the next start looks again. A file that is missing, cannot be read, or is not the one pinned stops the start before anything is spawned, with one error that names the file and says to reinstall (`modelProblemMessage()`): a damaged installation is reported rather than reaching the native library, which ends the engine's process on a model file it cannot read. A stop or a newer start during the check abandons the start. Show Diagnostics runs the same check, and its `Model:` line says what it found (`describeModelCheck()`). `scripts/verify-vsix.mjs` checks the packaged copies against the same pins, read from `dist/speechModel.js`, and fails a package that carries anything else under `models/`. No module of the extension imports a network module or calls `fetch`, which `tests/unit/speechModel.test.ts` asserts over every file in `src/`.

Earlier versions downloaded the model into global storage, under `sherpa-onnx/`, from this repository's `model-v1` release, which stays published for them. At every activation `removeDownloadedModel()` removes that copy: the files of the archive, each by name, the `version.txt` beside them, and an archive left by a download that did not finish, then each of their directories that is empty. A file put there by anything else stays, and so does everything else in global storage, the listener lock included. A file that cannot be removed, such as one open in a window still running an earlier version, is left for a later session; that window downloads the model again if it starts once its copy has gone. A removal that removed something writes one log line with the count and the size.

## Conventions

- TypeScript strict mode is enabled.
- No runtime npm dependency: everything the extension host runs is the extension's own code, the tokeniser included. `tests/unit/manifest.test.ts` pins an empty `dependencies`.
- All speech processing must remain local. No network calls for audio or recognition.
- Keep the extension under the `analytics-in-motion` publisher namespace.
- Avoid em dashes. Rewrite sentences to use a colon, semicolon, or separate sentence instead.

## Git Workflow

- `main` branch is what's published to the Marketplace. Keep it release-ready.
- Develop on feature branches, merge to `main` for releases.
- Commit message format: `type(scope): description` (e.g. `fix(engine): settle an awaited pause when the child exits`).
- Tag releases as `vX.Y.Z`. Publishing a GitHub release with such a tag runs `release.yml`, which builds, checks, and publishes the extension. A release whose tag does not start with `v`, such as the speech model's `model-v1`, which earlier versions download the model from and which therefore stays published, or `sherpa-onnx-v1.13.8`, which hosts the engine archives, runs nothing.
- `release.yml` has two jobs. The `release` job builds and checks on each of the four target legs, attaches to the release the `.vsix` that `scripts/verify-vsix.mjs` checked, and publishes that file to Open VSX with `ovsx publish <verified .vsix> --trusted-publishing`, which exchanges the job's OIDC ID token for an Open VSX token that expires within minutes and can publish only this extension, so the workflow needs no stored Open VSX token. The job declares `environment: open-vsx`, whose deployment rule admits only tags matching `v*`; the environment covers every step of the job. It also declares `permissions:` with `contents: write`, for checkout and the release upload, and `id-token: write`, for the ID token, and every permission not listed is withheld. The trusted publisher registered on open-vsx.org names this repository, the workflow file `release.yml`, and that environment. A registration cannot be edited, so renaming the file or the environment means deleting the registration and registering again. Open VSX matches a token to the registration by the numeric IDs of the repository and its owner, the workflow file, and the environment, not by the token's `sub` claim, so the format of the subject does not affect it. An Open VSX access token given with `-p`, `--pat`, or `OVSX_PAT` takes precedence over trusted publishing, so the job sets none. The registry compares the `publisher` field in `package.json` with the namespace exactly, case included.
- The `marketplace` job publishes to the Visual Studio Marketplace once every leg of the `release` job has succeeded. It runs on `ubuntu-latest` and declares `environment: microsoft-marketplace`, whose deployment rule admits only tags matching `v*`, and `permissions:` with `contents: read` and `id-token: write`. It downloads each target's `.vsix` from the release with `gh` and stops if a file's SHA-256 differs from the digest that GitHub recorded when the upload step attached it, so it publishes the files that the legs checked. It then signs in to Microsoft Entra ID as an app registration that is a Contributor member of the publisher: it requests the job's OIDC ID token for the audience `api://AzureADTokenExchange` and passes it to `az login --service-principal --federated-token <token> --allow-no-subscriptions`, with the Azure CLI that the runner image provides and the client and tenant IDs from the environment's secrets `AZURE_CLIENT_ID` and `AZURE_TENANT_ID`. The identity has a federated credential and no client secret, and holds no role on any Azure subscription. `vsce publish --azure-credential --packagePath <the four .vsix files>` then takes the identity's token from the Azure CLI; vsce reads each target platform from the package's manifest and refuses `--target` beside `--packagePath`, so the step gives none, and it packages nothing and runs no `vscode:prepublish` script. vsce uses a Personal Access Token given with `-p` or `VSCE_PAT` before `--azure-credential`, so the workflow gives none. The repository uses GitHub's immutable OIDC subject claims, so the federated credential's subject is `repo:analyticsinmotion@<owner ID>/wake-word@<repository ID>:environment:microsoft-marketplace`; renaming the environment, the repository, or its owner changes the subject, and the federated credential must then be changed to match. The identity's Marketplace User ID, which the publisher's Members page takes, is the `authenticatedUser.id` of `https://app.vssps.visualstudio.com/_apis/connectionData` read with the identity's token.
- On a re-run attempt, when `github.run_attempt` is not `1`, both publish steps add `--skip-duplicate`, so a re-run of the release, or of one of its jobs, does not fail on a target that an earlier attempt published: each step skips a target whose registry already has this version for it, and publishes the rest. vsce asks the Marketplace for the extension's versions before each upload and treats a 409 answer to the upload the same way. ovsx skips on the registry's answer that ends `is already published.`; Open VSX gives another answer for a version that it holds but has not activated, or has removed, and the step then fails. The first attempt leaves the flag out, so a version that is already published, such as one that `package.json` was not raised for, fails the publish steps; a new run of the same release, as opposed to a re-run, is a first attempt too. A leg that runs again builds a new package from the same commit, and the upload step replaces the release's asset of the same name with it, so a registry that published the version on an earlier attempt keeps the earlier package. The `marketplace` job needs every leg, so while a leg has failed, Open VSX has the targets of the legs that passed and the Marketplace has none. **Re-run failed jobs** runs the legs that failed and then the `marketplace` job, because GitHub re-runs a job's dependents with it; when only the `marketplace` job failed, it runs alone and publishes the release's current assets. **Re-run all jobs** also replaces the release assets of the legs that had succeeded.

## Testing

Automated tests run under [vitest](https://vitest.dev) with `npm test`. They
cover pure logic and the engine state machine: no microphone, no real child
processes, no network, and no VS Code API. `vitest.config.mts` aliases the
`vscode` module to `tests/mocks/vscode.ts` so src modules that import it can
still be loaded, and that stub throws if a test calls into the API without
stubbing that call with `vi.spyOn` first.

- `tests/unit/` is TypeScript and imports from `src/`.
- `tests/acoustic/` is JavaScript and covers the benchmark's own modules.
- The engine's own tests are Rust, run by `cargo test` in `engine-rs/`.

`tests/unit/engineLifecycle.test.ts` drives `SherpaEngine` end to end with
`child_process.spawn` mocked to return a `MockChildProcess`
(`tests/mocks/childProcess.ts`), the bundled model's check mocked to pass
unless a test says otherwise, and timers faked. The mock's `sendLine()`, `simulateExit()`, and
`simulateError()` stand in for the child, so start/stop/pause/resume, the
pause and resume commands on one child, the `PAUSED` and `RELEASED`
handshakes and their timeouts (verbs split across chunks included), the
promises `pause()` and `stop()` return and every way each settles, a pause
whose wait a stop takes over, a handoff driven through
`releaseThenFire()` that fires the command only after `PAUSED`, the
crash and retry backoff and its suppression while paused, the retry
cancellation in `stop()` and `pause()`, an `ERROR` before the engine has
listened reported once and one after it restarted, with the child's message
as the reason and the final error, `isStarting` and `restarting`, the bundled
model's directory in the config line, a model file missing or changed and a
stop during the check, a first start with no network request, the
`editorName` in the config line, and the debug timing lines are all asserted

which drives the races `tryAcquireLock()` closes one step at a time, and

`tests/unit/windowFocus.test.ts` checks `decideFocusLoss()` and

doing, and drives one and two windows through `activate()` with
`tests/mocks/editorWindows.ts`: each window in a module graph of its own,
with its own stubbed `vscode`, the real lock module bound to its own PID on a
storage directory the windows share, and a stand-in engine that keeps
SherpaEngine's state machine and opens a microphone the windows share, which

the resume, a window that is not focused when listening starts, a start or a

## Boundaries

**NEVER** add a runtime npm dependency.

**NEVER** send audio data over the network. All recognition is local.

**NEVER** add `darwin-x64` as a CI build target. Intel Mac (pre-2020) is excluded: the `macos-13` GitHub Actions runner has uncertain long-term availability, and `decibri` darwin-x64 support is unconfirmed. Revisit only if a darwin-x64 user files an issue.

CI and release build four targets: `win32-x64`, `darwin-arm64`, `linux-x64`, and `linux-arm64`. Linux ARM64 runs on the `ubuntu-24.04-arm` runner label, not a variant of `ubuntu-latest`, which is x64. Each engine is built on its own target's runner, so nothing is cross-compiled.

Both workflows run on Node 22 and build the engine on each target's own runner through `.github/actions/engine-rs`, then package, then run `scripts/verify-vsix.mjs` and the drive script against the unpacked `.vsix`; the release does this before anything is uploaded or published, and uploads and publishes the `.vsix` it checked. The rules that keep that artifact runnable:

- **NEVER** set `RUSTFLAGS` for the engine build or build it from outside `engine-rs/`: either loses `+crt-static` on Windows. The Windows build passes `-D linker-messages`, so LNK4098 (two C runtimes) fails it.
- **NEVER** build the Linux engine directly on the runner. It is built inside `quay.io/pypa/manylinux_2_28_*` so it needs nothing newer than glibc 2.28 and GLIBCXX 3.4.25, the editor's own Linux floor; `verify-vsix.mjs` fails a binary or ONNX Runtime that needs more.
- **NEVER** let the sherpa-onnx build script download its own archive, which is the official one with the text-to-speech components. `SHERPA_ONNX_ARCHIVE_DIR` points it at the archive `prebuilt.mjs` verified, and `prebuilt.mjs check` verifies the copy it unpacked. Bumping sherpa-onnx means building its archives with `engine-archives.yml`, publishing them on a `sherpa-onnx-v<version>` release, and pinning them in `engine-rs/scripts/pinned-inputs.mjs`; bumping the runtime files means new entries there too. `prebuilt.mjs` refuses a `Cargo.lock` version with no pinned archives.
- **NEVER** add a `.vscodeignore` line that matches `bin/`. `verify-vsix.mjs` fails a package without the engine or its runtime files, and one that carries anything under `node_modules`.
- The self-test exits 0 when ONNX Runtime or the Silero model is missing. Check what it reports, as `verify-vsix.mjs` does, never only its exit code.
- The runtime files set floors of their own: the macOS ONNX Runtime needs macOS 14.0. The Windows one imports the Visual C++ runtime (`msvcp140.dll`, `msvcp140_1.dll`, `vcruntime140.dll`, `vcruntime140_1.dll`), which is not part of Windows. Those libraries are **not** packaged: the Microsoft Visual C++ Redistributable is a requirement on Windows, stated in the README. **NEVER** start shipping them beside the binary. A copy there is resolved before the installed one, so it, and not the serviced copy, is what every user would load, and it would only change when this repository re-pinned it. `verify-vsix.mjs` fails a package that carries one. The same check pins the list above against the imports of the packaged files, so an ONNX Runtime bump that needs another library fails the package rather than a user's machine, and the README is revisited with the pin. Every CI runner has the redistributable, so no CI check shows what a machine without it does. The engine binary itself links the C runtime statically and imports none of them, which `verify-vsix.mjs` also checks.
- CI has no microphone: the drive script runs with `--no-microphone`, which skips the scenarios that open one.
- After the build, both workflows run the engine's Clippy lints and unit tests on every target through `.github/actions/engine-rs-checks`, in the target directory the build used. The sherpa-onnx build script links libraries already unpacked there rather than unpacking again, so the tests link the libraries the build unpacked from the verified archive, and the action runs `prebuilt.mjs check` afterwards as the build does. The rules above apply to these checks too: run from `engine-rs/`, no `RUSTFLAGS` (Clippy's `-D warnings` goes after `--`), and `SHERPA_ONNX_ARCHIVE_DIR` set. On Linux they run in the same `manylinux_2_28` image as the build, so the tests link with the compiler and C++ library the shipped binary is linked with. `cargo fmt --check` and ESLint run once, on the `linux-x64` leg.
- There is no `rust-toolchain` file, and adding one changes the compiler of the release build as well as of the checks. Windows and macOS build and check with the Rust release the runner image carries; the Linux image installs the current stable Rust each time. A new stable release can therefore add a Clippy lint that fails code nobody changed: fix the code, or allow that one lint where it is wrong with a comment saying why, rather than dropping `-D warnings`.
- `rust-version` in `engine-rs/Cargo.toml` is 1.88, the same as decibri 6.4.0's. No job compiles with it, because nothing that ships is compiled with it. Clippy's `incompatible_msrv` lint reads it and fails a standard library API newer than it; a dependency that raises its own minimum is not caught, so check decibri's `rust-version` when bumping it.
- `engine-archives.yml` builds Linux in a dated `manylinux_2_28` image, so its archives keep the engine's floors. Its runner images and that container image are pinned, and `build.sh` fixes the version of the Linux toolset it installs: a static library links only with a toolchain at least as new as the one that compiled it. Windows builds on `windows-2022` (MSVC 14.44), because objects from the Visual Studio 2026 toolset on `windows-latest` call standard library helpers that the 14.44 runtime library lacks. The engine may be linked with the same toolset or a newer one. `LINK_LIST` and `PLACEHOLDERS` in `engine-rs/archives/verify.mjs`, and `PLACEHOLDERS` in `build.sh`, follow the `sherpa-onnx-sys` build script's link list: check them whenever sherpa-onnx is bumped.
- **NEVER** compile the Linux archives with the image's default toolset, and never add or remove `-D_GLIBCXX_USE_CXX11_ABI=0` in `build.sh` for an architecture without reading the ONNX Runtime in that architecture's official archive. The libraries are linked into one executable with upstream's prebuilt ONNX Runtime, so they must match its compiler generation (GCC 11) and its `std::string` ABI, and the ABI differs by architecture: pre-C++11 on x64, hence the flag, and C++11 on aarch64, hence no flag. Libraries of the other ABI link without a message, and the engine then aborts with a corrupted heap whenever it loads the keyword spotting model; the self-test does not load that model, so it and `verify-vsix.mjs` still pass. A newer GCC changes what the keyword spotter detects. `verify.mjs` fails any archive whose libraries need a name from the linking toolchain that the official archive's do not, and a Linux archive whose libraries use another `std::string` ABI than its ONNX Runtime or record another compiler generation than the official archive's.
